# Database models and migrations

- Every table is declared `class X(Record, Base)`. `Record` gives it a UUID `id`, `created_at`,
  `updated_at` (all datetimes are timestamptz) and `deleted_at` (via `SoftDelete`). Nothing is hard-deleted.
- `Base` sets a naming convention for constraints, so name CHECKs briefly (`name="status"`); Alembic finds
  them by the generated name.
- Foreign keys used for scoping get an index (Postgres doesn't add one).
- Uniqueness is a **partial** unique index over live rows, built with `live_unique(table, *columns)`,
  never a plain UNIQUE, so a soft-deleted row doesn't block re-entry.
- Money is `Numeric`, never float. Fixed lists are text + a CHECK constraint generated from the `Literal`
  type in `models.py` (one definition drives the database, the API validation and the TypeScript unions).
- A polymorphic parent is several nullable real foreign keys plus a CHECK (`num_nonnulls(...) = 1`), not
  an `entity_type/entity_id` pair.

New tables are audited automatically (`app/audit.py`); decide which of their fields are sensitive
(`audit.REDACTED`). Defaults that mean "the moment of this write" use `clock_timestamp()`: `now()` is when the
transaction began, the same for every row in it.

To change the schema, follow the `add-migration` skill. Its essentials: **read the autogenerated
migration before running it**, prove the downgrade works, keep seeded ids stable, and remember that Render
runs migrations against the existing demo data.
